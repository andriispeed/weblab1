# Захист IT.SCHOOL — сценарій до 10 хвилин для 4 осіб

**Основна демонстрація: 9 хвилин 15 секунд. Запас: 45 секунд.** У час включені переходи між вкладками та короткий показ коду. Це орієнтир для репетиції, а не вимога читати текст із секундоміром. Якщо десять хвилин включають довгі запитання викладача, скоротіть показ коду за правилами наприкінці.

## Що підготувати до початку

1. Відкрити сайт, перевірити доступність і прибрати зайві вкладки. Використати один ноутбук; заздалегідь узгодити, хто керує мишею під час кожної частини.
2. Підготувати вкладки: головна; каталог без фільтрів; [CR15](https://telegrambot.vps.webdock.cloud/it-school/design); [форма Python](https://telegrambot.vps.webdock.cloud/it-school/contact?course=python); [адмінпанель](https://telegrambot.vps.webdock.cloud/it-school/admin); [Swagger](https://telegrambot.vps.webdock.cloud/it-school/api/docs/); README репозиторію.
3. Андрій заздалегідь входить у панель. Облікові дані бере зі свого приватного файла, який не потрібно відкривати на проєкторі. Зняти фільтри статусу й перевірити активну сесію.
4. У DevTools підготувати ширини **1440, 768 і 390 CSS px**. Не витрачати виступ на налаштування режиму пристрою. Вкладку форми після адаптивної демонстрації повернути до зручної ширини.
5. Підготувати вигадані дані: **Демо Захист**, **demo-defense@example.com**, Python, **Хочу дізнатися про курс Python**. До початку демонстрації нову заявку не надсилати.
6. У VS Code відкрити файли в порядку показу: `courses.ts`, `routes.ts`, `styles.scss`, `contact.ts`, `controllers.ts`, `security.ts`, `compose.yaml`. Повні шляхи є в особистих пам’ятках.
7. Провести одну спільну репетицію. Говорити паралельно з простими кліками; у коді зупинятися на потрібному методі, а не гортати весь файл.

`design-preview` прибрано з опублікованого сайту. `/design` — вебпорівняння CR15, а не Figma-макет. Якщо викладач окремо вимагає Figma, підготуйте справжній командний файл окремою вкладкою: вебстенд не замінює цю вимогу. Його короткий показ може зайняти частину блоку Дар’ї замість CSS; її роль залишається розробкою стилів сайту.

## 4. Андрій — 6:00–9:15

**На екрані:** Заявка в панелі → збережений статус → журнал → код і серверна схема.

### Текст

> Я відповідаю за бекенд, сервер, адмінпанель і взаємодію з API. Заявка, яку щойно надіслав Арсеній, проходить через HTTP-сервіс Angular до NestJS. Сервер повторно перевіряє поля й записує їх у PostgreSQL. Успішна відповідь містить номер заявки, тому підтвердження в інтерфейсі пов’язане зі справжнім записом у базі.
>
> Відкриваю панель команди й оновлюю список. Знаходжу демонстраційну заявку та звіряю її номер. Змінюю статус на «Зв’язалися», чекаю підтвердження й перезавантажую сторінку. Статус залишається, тому він збережений на сервері. У панелі також є пошук, фільтри, статистика, редагування ціни й опису курсів та історія адміністративних дій.
>
> У controllers.ts зміна статусу виконується в транзакції разом із записом журналу. Якщо одна частина операції не виконається, зміни скасовуються. Для редагування курсу використано номер версії: застаріла форма не може непомітно перезаписати нові дані. Повторне надсилання тієї самої заявки має унікальний requestId. Однаковий запит повертає той самий номер, а використання ключа з іншими даними викликає конфлікт.
>
> Доступ до панелі перевіряється не лише маршрутизатором Angular, а й серверним guard. Пароль зберігається як scrypt-хеш із сіллю. Після входу браузер отримує HttpOnly cookie, а адміністративні зміни додатково потребують CSRF-токена. Є перевірка джерела запиту та обмеження частоти входу й подання заявок.
>
> Застосунок опублікований на VPS через Nginx і HTTPS. Angular віддається як зібрані статичні файли. API та PostgreSQL працюють у Docker Compose, а база зберігає дані в окремому volume. API доступний Nginx через локальний порт, база не опублікована в інтернет. Проєкт використовує власний шлях і не заважає іншому сайту на сервері.
>
> Перед релізом створюється резервна копія, а щоденні копії запускає таймер. Є health endpoint із перевіркою бази, документація Swagger й автоматичні перевірки в GitHub Actions. У README розміщені посилання, запуск, розподіл ролей та рішення щодо вимоги замовника. Ми показали повний шлях від каталогу до збереженої й обробленої заявки. Дякуємо, готові відповісти на запитання.

```text
Браузер / Angular → HTTPS / Nginx → NestJS API → PostgreSQL
                                      ↑             ↓
                               Docker Compose   volume + backup
```

- **Втрачено до хвилини:** пропустити перемикання на код у перших трьох частинах. Залишити демонстрацію роботи й коротке усне пояснення.
- **Запитання займають до двох хвилин:** додатково пропустити перегляд `security.ts`, вкладки курсів і Swagger. Зберегти адаптивність, CR15 та «заявка → статус → перезавантаження».
- **Немає заявки в панелі:** прибрати фільтр статусу, перевірити пошук, натиснути «Оновити», звірити номер із квитанцією. Після репетицій можуть бути однакові імена — орієнтуватися на номер.
- **Сесія завершилася:** повторно ввійти; заявка від цього не зникає. Поки Андрій входить, інший учасник може пояснити вже показаний фрагмент коду.
- **Немає успішної відповіді форми:** показати помилку й спробувати після відновлення зв’язку. Не говорити, що заявку прийнято без квитанції.
- **Немає мережі:** пояснити, що поточна live-демонстрація недоступна; показати код і збережені результати перевірок із зазначенням, що це попередній запуск.

## Межі тверджень на захисті

Це навчальний сайт зі справжнім збереженням заявок, а не повна LMS. Оплати, автоматичних листів і гарантії вступу немає. Палітра має розрахунок контрасту, але сайт не проходив повний аудит WCAG. Не вигадуйте оцінки Core Web Vitals чи результати дослідження конверсії. Пояснення стандартів і джерела наведені в [CHANGE_REQUEST.md](CHANGE_REQUEST.md) та [пам’ятці Дар’ї](defense/DARIA.md). GitHub Actions перевіряє проєкт, а deploy на VPS виконується окремими скриптами. Особистий внесок описуйте відповідно до фактичної роботи, використовуючи карту відповідальності за спільними файлами.
