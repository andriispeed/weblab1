# Шкіндер Андрій — бекенд, сервер, адмінпанель та API

Твій виступ: **6:00–9:15**, після Арсенія. До 10:00 залишається запас на затримки або коротке запитання. Усі погоджені задачі залишені за тобою: **NestJS, PostgreSQL, сервер, розгортання, адмінпанель і взаємодія Angular з API**.

## Що ти представляєш

Ти показуєш повний шлях даних: форма → HTTP-сервіс Angular → Nginx → NestJS → PostgreSQL → адмінпанель. Арсеній відповідає за зручність форми й клієнтські перевірки, але її API-виклик, серверне приймання, захист від дублювання та подальша обробка — твоя частина.

Наведені файли — карта закріпленої реалізації. У спільних файлах пояснюй свою частину, а не заявляй одноосібне авторство всього файла. У тебе найбільша зона, тому на виступі показуй один завершений сценарій; детальні таблиці нижче призначені для підготовки й запитань.

## Архітектура простими словами

```text
Браузер: Angular
  ├─ GET /it-school/...       → Nginx → файли frontend
  └─ /it-school/api/...       → Nginx → 127.0.0.1:3100
                                             ↓
                                      NestJS у Docker
                                             ↓
                                  PostgreSQL у приватній мережі
                                             ↓
                                      Docker volume database
```

Nginx працює перед API: він приймає HTTPS, віддає зібрані Angular-файли та проксіює API-запити. Контейнер API слухає `0.0.0.0:3100` **всередині контейнера**, а на хості порт опублікований тільки як `127.0.0.1:3100`. PostgreSQL не має публічного порту в Compose. Інший проєкт на сервері продовжує працювати; наш сайт займає окремий префікс URL.

## 1. Запуск API: main.ts

`AppModule` реєструє три контролери та провайдери `Database`, `AuthService`, `AdminGuard`, `RateLimit`. Dependency injection дозволяє контролеру отримати готовий екземпляр сервісу через конструктор.

`bootstrap()` послідовно:

1. Читає `PUBLIC_URL` і створює NestExpressApplication.
2. Встановлює довіру до одного проксі; вимикає заголовок `x-powered-by`, підключає Helmet.
3. Вмикає JSON parser із лімітом **16 KB**.
4. Для запитів зміни перевіряє точну відповідність `Origin`; крім DELETE, вимагає JSON. Ставить `Cache-Control: no-store` для API.
5. Додає префікс `api` та глобальний `ValidationPipe`: `transform`, `whitelist`, `forbidNonWhitelisted`.
6. Створює Swagger-документацію. Інтерактивне виконання запитів у цьому Swagger вимкнене через `supportedSubmitMethods: []`.
7. Ініціалізує застосунок і початкового адміністратора, починає слухати порт 3100.

`whitelist` визначає дозволені поля DTO, а `forbidNonWhitelisted` відхиляє зайві. `transform` передає контролеру об’єкт відповідного DTO; правила типів усе одно задають декоратори. Сам TypeScript-інтерфейс не перевіряє дані під час HTTP-запиту.

## 3. База й транзакції

У `Database` використано драйвер **pg** і прямі SQL-запити. Це не TypeORM/Prisma, хоча міграція оформлена окремим класом.

| Метод | Що робить і навіщо |
|---|---|
| `constructor()` | Додає обробник помилок неактивних з’єднань пулу. |
| `onModuleInit()` | Перевіряє пароль БД, відкриває транзакцію, бере advisory lock і запускає початкову міграцію, якщо її ще немає в таблиці `migrations`. Lock захищає від одночасної ініціалізації. |
| `query(sql, args)` | Виконує параметризований запит і повертає `rows`. |
| `transaction(work)` | Бере одне з’єднання; виконує `BEGIN`, функцію `work`, потім `COMMIT`. При помилці — `ROLLBACK`; у `finally` завжди повертає з’єднання до пулу. |
| `onModuleDestroy()` | Закриває пул при штатному завершенні. |

Пул має максимум 5 з’єднань, таймаут з’єднання 5 секунд, SQL-запиту 10 секунд. Пул повторно використовує з’єднання, замість створювати нове для кожної операції.

У `Initial1795000000000.up()` створюються:

| Таблиця | Що зберігає |
|---|---|
| `courses` | Курси; `modules` у JSONB, `version` для перевірки конкурентного редагування. |
| `applications` | Контактні дані, курс, статус, час, унікальний `request_id`, fingerprint. `course_id` — зовнішній ключ, для консультації може бути NULL. |
| `admin_users` | Ідентифікатор, унікальний логін і хеш пароля. |
| `sessions` | Хеш токена, адміністратор, CSRF і час завершення сесії. |
| `audit_log` | Тип адміністративної дії, об’єкт, деталі й час. |

Технічна `migrations` створюється в `Database.onModuleInit()`. Початкові три курси додаються тільки під час першої міграції. Індекси прискорюють вибірку заявок за часом/статусом і пошук прострочених сесій. `down()` навмисно кидає помилку: автоматичного руйнівного відкату схеми немає.

**Навіщо `$1`, `$2` у SQL:** текст запиту та значення передаються окремо. Значення користувача не конкатенуються як SQL-команди. У пошуку додатково екрануються `%`, `_` та зворотна риска, щоб вони не ставали довільними LIKE-шаблонами.

## 4. Кожен метод контролерів

У таблиці шляхи наведено відносно зовнішнього `/it-school/api/`.

| Метод | HTTP | Поведінка |
|---|---|---|
| `PublicController.health()` | GET `health` | Виконує `SELECT 1`; повертає стан API й БД. Це більше, ніж просто перевірка відкритого порту. |
| `courses()` | GET `courses` | Повертає курси за `position`. |

| `AdminController.applications()` | GET `admin/applications` | Перевіряє фільтри; пошук за ім’ям, email або назвою курсу; 20 записів на сторінку; загальна статистика. |

| `editCourse()` | PATCH `admin/courses/:id` | Оновлює ціну й опис лише за збігу версії, збільшує version і додає `course.update`. Якщо оновлення не виконане — 409. |
| `audit()` | GET `admin/audit` | Повертає 30 останніх адміністративних подій. |

`stats` у списку заявок — статистика **всіх заявок**, а `total/items` враховують поточний фільтр. Тому числа можуть відрізнятися. `@UseGuards(AdminGuard)` стоїть на всьому AdminController: прямий запит без сесії теж не допускається.

### Як не створити дві однакові заявки

`ContactPage` створює UUID `requestId` і повторно використовує його при повторі спроби. Сервер рахує SHA-256 fingerprint нормалізованих імені, email, курсу й повідомлення. У БД `request_id` має UNIQUE; `ON CONFLICT(request_id) DO NOTHING` не вставляє другий запис. Після цього сервер читає наявний запис:

- той самий ключ і дані → повертає той самий номер;
- той самий ключ, інші дані → **409 Conflict**;
- новий ключ → нова заявка.

Це називається **ідемпотентністю повторної операції**. Вона працює за ключем, а не за однаковим email. Після повного перезавантаження форми створюється новий ключ; це не глобальний захист від усіх дублікатів контактів.

### Конкурентне редагування курсу

У SQL є `WHERE id=$3 AND version=$4`. Якщо два адміністратори відкрили версію 1, перший збереже версію 2. Другий зі старою версією 1 отримає 409 і має оновити список. Це оптимістичний контроль версії; він запобігає тихому перезаписуванню чужих змін.

## 5. Авторизація і безпека: security.ts

| Функція або метод | Пояснення |
|---|---|
| `digest(value)` | SHA-256 для випадкового токена сесії. Це не функція хешування пароля. |
| `initializeAdmin()` | Якщо адміністратор уже існує — нічого не робить. Інакше читає початковий пароль, створює сіль і scrypt-хеш та записує обліковий запис. Зміна env після створення не змінює пароль автоматично. |
| `AuthService.login()` | Знаходить користувача, обчислює scrypt і порівнює через `timingSafeEqual`. Створює випадкові токен і CSRF, прибирає прострочені сесії, записує нову на 8 годин. |
| `identify(req)` | Читає cookie, перевіряє формат токена, шукає його хеш і непрострочену сесію; заповнює `req.admin`. Інакше 401. |
| `logout(tokenHash)` | Видаляє відповідну сесію. |
| `AdminGuard.canActivate()` | Перевіряє сесію; для методів зміни перевіряє `X-CSRF-Token`. При неправильному CSRF — 403. |
| `RateLimit.check(key, max, windowMs)` | Лічить запити в часовому вікні; після ліміту — 429. Використовується ключ із IP. |

Ліміти: **12 спроб заявки за 15 хвилин**, **8 спроб входу за 15 хвилин**. Лічильники знаходяться в пам’яті API, скидаються після перезапуску й не синхронізуються між кількома інстансами. Для поточного одного API це проста реалізація; для масштабування потрібне спільне сховище лімітів.

Cookie `it_school_session`: `HttpOnly` не дає JavaScript читати токен; `Secure` обмежує передачу HTTPS; `SameSite=Strict` обмежує передачу в міжсайтовому контексті; `Path=/it-school/` задає шлях. У базі зберігається хеш токена, а не його оригінал. CSRF перевіряється для адміністративних змін, Origin — для всіх запитів зміни, включно з публічною заявкою.

## 6. Angular ↔ API: core/api.ts

`Api.base` обчислюється як `new URL("api/", document.baseURI)`, тому запити враховують базовий шлях `/it-school/`. `HttpClient` повертає типізовані Observable. Інтерфейси `Course`, `Application`, `ApplicationList`, `Receipt`, `Session`, `Audit` описують очікувану форму даних; runtime-валідацію запиту виконує бекенд.

| Метод Api | Призначення |
|---|---|
| `courses()`, `course(id)` | Каталог і конкретний курс; id кодується через `encodeURIComponent`. |
| `apply(data)` | POST заявки, відповідь типу `Receipt`. |
| `me()`, `login(data)`, `logout()` | Перевірка сесії, вхід, вихід. |
| `applications(status, q, page)` | Отримання списку з query-параметрами. |
| `status(id, status)`, `remove(id)` | Зміна статусу та видалення заявки. |
| `editCourse(id, data)` | PATCH ціни, опису та версії курсу. |
| `audit()` | Список адміністративних подій. |

`SecurityState.session` зберігає username і CSRF у пам’яті Angular. Секретний токен сесії зберігається в HttpOnly cookie. `securityInterceptor` додає `X-CSRF-Token` лише до запитів нашого API, які не є GET/HEAD, коли сесія відома.

`adminGuard` викликає `me()`, зберігає сесію й дозволяє маршрут; при помилці очищує стан і повертає UrlTree на `/admin/login`. Це зручність навігації, **не заміна серверного guard**.

`errorMessage(error)` перетворює HTTP-помилки на текст: status 0 — немає з’єднання, 5xx — сервіс недоступний, рядкове серверне message — показати його, 400 — перевірити поля, решта — загальне пояснення.

`LoginPage.submit()` перевіряє форму, блокує повторну спробу, викликає API; у разі успіху встановлює `SecurityState` та переходить до `/admin`, при помилці повертає кнопку й показує текст.

В `admin.html` треба вміти знайти прив’язку селекта статусу до `changeStatus`, підтвердження видалення та форму редактора курсу.

## 8. Інфраструктура, реліз і backup

`compose.yaml` запускає PostgreSQL 17 і API. Постійний volume `database` зберігає дані при заміні контейнера. API починає роботу після здорової БД. Для невеликого VPS задані ліміти пам’яті, процесів і журналів. API працює з read-only файловою системою та тимчасовим `/tmp`.

`nginx-location.conf` передає `/it-school/api/` на локальний `/api/`, а для Angular використовує `try_files ... /it-school/index.html`: пряме відкриття `/courses/python` завантажує SPA. Старий `/design-preview` повертає **410 Gone**, файли макетів не входять у вебреліз. HTTPS використовує наявну конфігурацію сервера.

| Скрипт / функція | Що робить |
|---|---|
| `package-release.mjs` | На верхньому рівні створює id релізу, копіює зібрані frontend/backend та infra, пакує tar.gz, записує `latest.json`. Окремої функції `package()` немає. |
| `deploy.ps1` | Перевіряє id і SSH-ключ, завантажує архів та Python-скрипт через scp, запускає віддалений deploy. Кожний зовнішній крок перевіряє код завершення. |
| `deploy.py: run()` | Запускає зовнішню команду з `check=True`; помилка перериває нормальне виконання. |
| `compose()` | Формує Docker Compose-команду для потрібного релізу й runtime.env. |
| `write_private()` | Записує конфігураційний файл із правами 0600. |
| `replace_link()` | Створює нове тимчасове символічне посилання й замінює поточне. |
| `main()` | Перевіряє шляхи, розпаковує реліз, робить backup перед оновленням, запускає контейнери, перевіряє API, перемикає current, перевіряє й перечитує Nginx. При помилці намагається повернути попередні код і конфігурацію. |
| `backup.sh` | `pg_dump -Fc` у тимчасовий файл; після успіху перейменовує його та зберігає 14 найновіших непорожніх dump-файлів за відповідним шаблоном. До цієї ротації можуть входити й backup перед релізами. |
| `it-school-backup.timer` | Запуск щодня о 03:20 UTC із випадковою затримкою до 5 хвилин; Persistent дозволяє надолужити пропущений запуск. |

Відкат коду **не відкочує автоматично дані або схему БД**. Для відновлення бази є окрема процедура в [OPERATIONS.md](../OPERATIONS.md). Volume не замінює backup, backup на тому самому VPS не замінює зовнішню копію.

GitHub Actions автоматично збирає проєкт, перевіряє production-залежності, запускає API-тести з окремою PostgreSQL і перевіряє локальний генератор Figma. Workflow **не виконує автоматичний deploy** на VPS; публікація відбувається через скрипти.

## Текст виступу

> Я відповідаю за бекенд, сервер, адмінпанель і взаємодію з API. Заявка, яку щойно надіслав Арсеній, проходить через HTTP-сервіс Angular до NestJS. Сервер повторно перевіряє поля й записує їх у PostgreSQL. Успішна відповідь містить номер заявки, тому підтвердження в інтерфейсі пов’язане зі справжнім записом у базі.
>
> Відкриваю панель команди й оновлюю список. Знаходжу демонстраційну заявку та звіряю її номер. Змінюю статус на «Зв’язалися», чекаю підтвердження й перезавантажую сторінку. Статус залишається, тому він збережений на сервері. У панелі також є пошук, фільтри, статистика, редагування ціни й опису курсів та історія адміністративних дій.
>
> У controllers.ts зміна статусу виконується в транзакції разом із записом журналу. Якщо одна частина операції не виконається, зміни скасовуються. Для редагування курсу використано номер версії: застаріла форма не може непомітно перезаписати нові дані. Повторне надсилання тієї самої заявки має унікальний requestId. Однаковий запит повертає той самий номер, а використання ключа з іншими даними викликає конфлікт.
>
> Доступ до панелі перевіряється не лише маршрутизатором Angular, а й серверним guard. Пароль зберігається як scrypt-хеш із сіллю. Після входу браузер отримує HttpOnly cookie, а адміністративні зміни додатково потребують CSRF-токена. Є перевірка джерела запиту та обмеження частоти входу й подання заявок.
>
> Застосунок опублікований на VPS через Nginx і HTTPS. Angular віддається як зібрані статичні файли. API та PostgreSQL працюють у Docker Compose, а база зберігає дані в окремому volume. API доступний Nginx через локальний порт, база не опублікована в інтернет. Проєкт використовує власний шлях і не заважає іншому сайту на сервері.
>
> Перед релізом створюється резервна копія, а щоденні копії запускає таймер. Є health endpoint із перевіркою бази, документація Swagger й автоматичні перевірки в GitHub Actions. У README розміщені посилання, запуск, розподіл ролей та рішення щодо вимоги замовника. Ми показали повний шлях від каталогу до збереженої й обробленої заявки. Дякуємо, готові відповісти на запитання.

## Питання та готові відповіді

- **Чому NestJS?** Структуровані контролери, DI, DTO, guards та документація API; TypeScript і на фронтенді, і на бекенді.
- **Чому PostgreSQL?** Заявки пов’язані з курсами, потрібні обмеження, транзакції та надійне збереження.
- **Де ORM?** Тут її немає: драйвер pg, параметризований SQL і власний невеликий механізм міграції.
- **401, 403, 409 — різниця?** 401 — немає дійсної сесії; 403 — операція не дозволена, наприклад неправильний CSRF/Origin; 409 — конфлікт ключа заявки або версії курсу.
- **Чи захищає Angular guard API?** Ні. Він керує навігацією, а серверний guard перевіряє кожний захищений запит.
- **Навіщо CSRF, якщо є HttpOnly?** HttpOnly забороняє читати cookie JavaScript-коду, але cookie браузер надсилає сам. CSRF-токен і перевірка Origin контролюють запити зміни.
- **Чи зникнуть дані при перезапуску?** Не від звичайного перезапуску контейнера: вони у volume. Видалення тому або пошкодження диска — інша ситуація, для якої потрібні backup.
- **Курси в панелі оновлюються в усіх вкладках миттєво?** Дані зберігаються в БД, але відкритий каталог не має WebSocket. Нові значення видно після наступного завантаження його даних.
- **Чи статус «Зараховано» означає реальну оплату?** Ні, це статус навчальної заявки; платежів, LMS і автоматичних листів немає.
- **Що з масштабуванням?** Зараз один API на VPS. Для кількох інстансів треба, зокрема, спільний rate limiter, керування міграціями, моніторинг і зовнішні резервні копії.

Перед захистом пройди сценарій разом з Арсенієм. Вмій пояснити `apply → UNIQUE request_id`, `status → transaction`, `login → cookie`, `guard → csrf`, `Api.status → PATCH`, `Nginx → localhost → Docker → PostgreSQL` без читання всього файла.
